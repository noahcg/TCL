# Private editorial studio

Run `npm run admin`, then open **http://127.0.0.1:4174/admin/**. The command builds the site and starts a separate server bound to this computer’s loopback address. The studio has no public navigation link and is never copied into `dist/` or deployed to Vercel/Netlify. `npm run dev` continues to run the ordinary public-site preview.

The studio loads `OPENAI_API_KEY` from your ignored `.env.local` or shell. The existing image-generation key works here too. No key is sent to the browser. Optional settings are `TCL_EDITOR_MODEL` (default `gpt-6.2-astra`, requiring web search and structured outputs) and `TCL_ADMIN_PORT` (default `4174`). Restart the server after changing these settings. API calls use your OpenAI API billing; a scan performs one web-research request and one idea-formatting request, and each draft uses one more request. Requests are never automatically retried.

1. Choose MDN, Kevin Powell’s website and YouTube videos, Ahmad Shadeed, web.dev, and/or CSS-Tricks. Add an optional topic and choose a research window.
2. Click **Scan the CSS web**. The server uses [live web search with domain filters and source lists](https://developers.openai.com/api/docs/guides/tools-web-search). It prefers recent material, permits older reference documentation for context, and passes your existing published and draft content to avoid repeated angles. Source coverage is shown in research history. A source with no cited results does not imply every page on that site was checked.
3. Review article and Quick Win ideas, the proposed outline, browser-support caveats, original source links, and related existing coverage. Ideas with no verifiable search source are rejected. **Set aside** keeps an idea out of the active board; it can be restored later.
4. Click **Generate article** or **Generate Quick Win**. The draft opens in an editor with title, summary, tags, Markdown, and a sanitized formatting preview. Quick Wins also include a CSS snippet, difficulty, and fallback note. Generating again for an existing idea opens its draft rather than charging for a replacement.
5. **Save draft to content** writes a validated `status: "draft"` JSON record to `content/authored/<type>-<slug>.json`. Drafts remain excluded from the public build and search. Once saved, a URL slug stays fixed. Other content files and published records cannot be overwritten through the studio.
6. After checking the code, facts, attribution, and current browser support, check the review box and click **Add to local site**. Articles generate unique artwork through the existing image pipeline, using API credits, unless matching artwork already exists. Quick Wins do not require artwork. The item becomes published and the local site rebuilds. A failed build restores the draft record and attempts to restore the previous preview; generated artwork may remain cached. This action does not push to Git or deploy the live website.

Review the local preview with **View local site**, then use **Review live publication** to prepare a production update. AI produces original teaching drafts from the researched angle; it does not promise that code has run, videos have been watched, or support claims have been independently verified. Review these before publication.

## Approve and publish live

After **Add to local site** completes, choose **Review live publication** on the draft card or inside its editor. The studio creates an isolated release from your current committed `main`, adds just the selected content and its artwork, and runs `npm run verify` against that exact candidate. It merges only that article’s image-catalog entry; other pending articles and unrelated local edits stay out of the release.

The review shows the destination repository and branch, the checked commit, the files, and an expandable content diff. Preparing a release makes no changes to the live site or your working branch. Check **I approve this content and the listed files for the live website**, then click **Approve & publish live** to publish that checked commit. Changes to the content, staging area, or branches after preparation require a fresh review.

Approval adds the release commit to your local `main` while preserving other staged edits and working files, then pushes it to `origin` and finally the `vercel` remote. Vercel’s existing Git integration handles the production deployment. The studio reports **Sent for live deployment** and links to the commit’s deployment checks; submission does not mean the hosted build has already finished. Set `TCL_SITE_URL` to your production HTTPS origin to also get an **Open live page** link. The manual [deployment workflow](deployment.md) remains available.

This uses your existing local Git identity and GitHub HTTPS/SSH authentication; no Vercel API token is needed. Both remote `main` branches must match your local `main` before preparation. The default production remote is `vercel`; override it with `TCL_LIVE_REMOTE` if needed. Embedded credentials in remote URLs are rejected. Git operations do not force-push, merge conflicting history, or collect browser credentials. If a push stops partway through, review and retry the same release: completed pushes are detected and reused. The checked release is retained in ignored `.tcl-admin/releases/` for review and retry.

Research history and working drafts persist in ignored `.tcl-admin/state.json`. These files stay on this computer and are not a cross-device CMS. Saved content and generated article artwork live in the normal source folders for Git review. Back up `.tcl-admin/` separately if you want to retain research history.

The server checks its exact loopback Host, rejects cross-site requests, and requires a per-process session token on API requests. This is a local tool: do not expose its port through a tunnel or reverse proxy. Only one studio process can run at a time. Stop it with Ctrl+C. If a process was killed without cleanup, confirm it has stopped before removing `.tcl-admin/server.lock`. Reload the browser after restarting the server to get a new session token.
